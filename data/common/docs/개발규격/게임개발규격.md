## 1. 대상 플랫폼·실행·시험 장소 — Android APK 가 기본 (골격 0·7절에 더함)

- **모든 게임의 기본 대상은 Android 기기용 APK 다**(사용자 기본값, 2026-11-04). iOS·desktop(Windows·macOS·Linux)은 **사용자가 정할 때만** 확장한다 — 정하기 전에는 만들지 않는다(desktop 빌드·desktop 전용 조작 기능 포함). 기획이 따로 정하면 기획을 따른다.
- **빌드·에뮬레이터는 CI(GitHub Actions)에서, 플레이는 사용자 폰에서.** CI 가 APK 빌드·자동 시험·에뮬레이터 점검을 하고, 사용자는 **릴리스(태그)에 붙은 APK** 를 폰에 설치해 본다(7절). 작업 서버(에이전트가 일하는 곳)에서는 게임 실행·Android 빌드·에뮬레이터를 돌리지 않는다 — 골격 0절 "개발 환경"의 "배포 대상 OS·기기를 여기서 돌릴 수 있는지"에 이렇게 적는다. 작업 서버에서는 **화면 없는 전체 검증**(4절 A 단위 + B headless 통합 — 9절)을 돌려 CI 분량을 아끼고, CI 는 같은 검증을 다시 돌린 뒤 APK 빌드·에뮬레이터 점검을 맡는다.
- **CI 분량을 아낀다.** 비공개 저장소의 Actions 무료 시간은 계정 전체가 같이 쓴다. push 마다 빌드하지 말고 경로 필터·수동 실행(`workflow_dispatch`)·캐시를 쓴다. 에뮬레이터 점검은 마일스톤·태그 때.
- 엔진·도구는 **Android APK 를 CI 에서 내보낼 수 있는 것**으로 고른다. 첫 Phase 에서 빈 장면 APK 를 CI 로 만들어 프리릴리스에 붙이고, 사용자가 폰에 설치해 띄워 본다(확인 일자·기기·엔진 버전을 CLAUDE.md 0절에).
- CLAUDE.md 0절 "운영 환경"에 적는다: minSdk·targetSdk·ABI(기본 arm64-v8a)·화면 방향(가로·세로 — 기획)·사용자 폰 기종·에뮬레이터 API 수준. CI 워크플로 파일과 수동 실행 방법은 골격 7절 "1차 실행 경로"에.
- 키보드·마우스 입력은 개발 중 편의로만 둔다(출시 기능이 아니다).
- 확장을 정하면: iOS 는 macOS + Xcode + Apple 개발자 계정이 있어야 한다(Actions 의 macOS 러너는 분량을 10배로 센다) — 환경이 없으면 보류 결정에 올린다. desktop 은 같은 코드에서 내보내고 입력(키보드·마우스·패드)을 더한다.

## 2. Phase = 마일스톤 (`howtoWORKFLOW.md` 1·2절 바꿈)

- 기획서의 마일스톤(예: M0·M1 …)을 Phase 로 본다. 이름·번호는 기획서를 따른다.
- **첫 Phase 는 늘 '조사 + 기술 검증'.** 이미 있는 저장소면 CLAUDE.md·문서·코드·테스트·빌드 설정·CI 를 읽고, 기획과 다른 점·이 문서와 다른 점을 `docs/기획_차이.md` 로 만든 뒤 멈춘다(조사 전엔 코드를 고치지 않는다). 새 저장소면 빈 장면 → 입력 하나 → CI 가 만든 APK 를 프리릴리스(예: `v0.1.0-rc.1`)에 붙임 → 사용자 폰에서 실행까지 끝까지 통과시킨다(`howtoWORKFLOW.md` 1절 Phase 1 의 끝나는 조건 "빈 골격에서 검증 명령이 통과한다"의 게임판).
- 프로토타입(`howtoWORKFLOW.md` 1절 "프로토타입을 권할 때" 표에 더함): 조작감·재미가 결과를 좌우하면 **핵심 루프 하나를 폰에서 해 볼 수 있는 수직 슬라이스**를 권한다.
- 완료 기준(`howtoWORKFLOW.md` 1절 "끝나는 조건")에 늘 넣는다: 화면 없는 전체 검증 통과(작업 서버·CI) + **릴리스의 APK 를 사용자가 폰에 설치해 '1분 플레이 경로'를 끝까지** + 스크린샷(CI 에뮬레이터·사용자 폰).
- **겉동작을 바꾸지 않는 마일스톤**(구조 정리·리팩터·엔진 판 올리기): 기능 대신 '바뀌지 않았다'를 완료 기준으로 둔다 — 바꾸기 전에 같은 시드·같은 입력 기록으로 골든(상태 해시·화면 해시)을 떠 두고, 바꾼 뒤 같은지 본다(4절 입력 리플레이 회귀). 화면 해시(픽셀)는 같은 OS·같은 그리기 방식끼리만 비교한다 — 다르면 상태 해시만 본다. 폰 확인 목록은 1분 플레이 경로만.

- 설계서는 새 모듈·새 데이터 형식·새 저장 형식이 생길 때만 쓴다. 인터뷰결과서는 기획이 없을 때만.
- 게임 고유 문서(필요할 때 — 골격 9절 "이 프로젝트에만 필요한 문서"에 적는다): `docs/그림규격.md`(크기·방향 수·프레임·팔레트·타일 — 도트 그림이면 이름을 `docs/도트규격.md` 로 해도 된다)·`docs/조작.md`(입력 표)·`assets/ASSETS.md`(6절)·`docs/성능.md`(5절 예산·실측).
- 마지막 Phase 가이드 3종(`howtoDELIVERABLE.md` 1.2절): 설치 및 실행 가이드 = APK 받기(릴리스 한 곳 — 골격 7절 "사용자가 받을 배포물". CI 결과물로 안내하지 않는다)·폰에 설치(출처를 알 수 없는 앱 허용)·첫 실행·업데이트 설치(옛 세이브 유지) / 사용자가이드 = 플레이 가이드(조작·목표·저장) / 운영자가이드 = 서버가 있을 때만 채운다. 없으면 8절 인수인계(서명 키 보관 위치 — 7절)만 쓰고 나머지 절은 "해당 없음".

## 4. 시험 (골격 3·5절 바꿈)

| 등급 | 게임에서 | 규칙 |
|---|---|---|
| A 핵심 순수 로직 | 공식·판정(피해·명중·상태)·등급·성장·경제·데이터 읽기·세이브 직렬화 | 테스트 먼저. 작업 서버와 CI 둘 다에서 돈다. 상류(공용 데이터)가 같은 결과 시험 값(골든)을 주면 반드시 자기 시험에 넣는다 |
| B 오케스트레이션 | 장면 전환·상태 기계·입력 → 행동·AI·저장·불러오기 흐름 | headless 로 N 프레임 돌리는 통합 시험·스크립트 입력 — **작업 서버(headless)와 CI 둘 다에서** |
| C 콘텐츠 | 그림·애니·소리·연출·맵·대사 | 검사 스크립트(자산 목록·크기·프레임 수·누락·출처) + 스크린샷(작업 서버의 화면 없는 그리기·CI 에뮬레이터 — 5절 확인) |

- **커버리지**는 골격 3절 값 그대로다(A ≥ 90%·B ≥ 70%·C 측정 제외) — 게임이라고 낮추지 않는다. 엔진이 돌려야 하는 장면 코드는 B 로 headless 시험에서 잰다.
- **SOLID 의 게임판**(골격 2절 — 프로젝트 CLAUDE.md 2절에 옮겨 적는다): 판정(A)은 순수 함수로 두고 엔진·화면 모듈을 가져오지 않는다. 장면은 상태 기계와 부품 연결만 하고 판정을 직접 계산하지 않는다. 가장 바뀌기 쉬운 두 축은 콘텐츠 데이터(인물·기술·맵·대사 — 코드 수정 없이 데이터로 늘린다)와 화면·입력(엔진·기기에 따라 바뀐다)이다.

- **판정은 플랫폼과 무관하게.** 고정 시간 간격(고정 dt)으로 진행하고, 난수는 시드 하나에서 나눠 쓴다. 나눠 쓸 시드를 만들 때 실행(프로세스)마다 달라지는 값을 쓰지 않는다 — 예: Python 내장 `hash()`(문자열은 프로세스마다 다르다)·객체 주소(`id()`)·시드 없는 난수 생성기·현재 시각. 이름에서 시드를 만들려면 안정된 해시(예: CRC32·SHA 계열)를 쓴다. 같은 시드·같은 입력 기록이면 같은 상태 해시(작업 서버·CI 의 headless·에뮬레이터와 사용자 폰이 같아야 한다 — 부동소수가 갈리면 정수·고정소수로 바꾸거나, 같은 기기끼리만 비교한다고 적는다).
- **입력 리플레이 회귀**: 입력 기록(프레임·입력)을 시험 자료로 두고, 바꾼 뒤에도 같은 결과인지 본다.
- **headless**: 창 없이 돌리는 명령을 CLAUDE.md 0절에 적는다(엔진마다 다르다 — 예: SDL 계열 `SDL_VIDEODRIVER=dummy`, Godot `--headless`). 작업 서버와 CI 둘 다에서 돈다 — 작업 서버엔 엔진·가상환경을 깃 무시 폴더(예: `.venv`·`.tools`)로 둔다.
- **세이브 호환**: 세이브에 형식 버전·받은 데이터 판을 적고, 옛 세이브 불러오기 시험을 둔다 — 상류가 id 를 폐기·합치면 옮기는 시험까지(`howtoWORKFLOW.md` 4절 "더하기·바꾸기·빼기를 모두 시험한다").
- **폰 확인**: 마일스톤마다 사용자가 릴리스의 APK 를 폰에 설치해 확인 목록(1분 플레이 경로·일시정지 → 재개·회전(지원하면)·저장 → 앱 종료 → 불러오기)을 해 본다. 에이전트는 확인 목록과 릴리스 주소를 주고, 사용자가 알려 준 결과를 테스트결과서에 옮긴다. CI 에뮬레이터 점검의 스크린샷·로그는 짧게 두는 CI 결과물이라, 테스트결과서에 남길 몇 장은 `docs/screenshots/<마일스톤 id>/` 에 옮긴다(`howtoDIRECTORY.md` 2절).

## 5. 화면·입력·성능 (골격 4절 "화면 (UI/UX)" 바꿈 — 웹 기준 대신)

- **화면**: 기준 해상도 하나와 비율 대응(폰 16:9 ~ 20:9·태블릿 4:3), 안전 영역(노치·펀치홀·제스처 바), 도트면 정수 배율, 가장 작은 글자 크기. 실행 중 화면 크기·비율이 바뀌는 기기(접는 폰의 접기·펴기 등)를 지원하면 바뀐 뒤에도 그림·터치 자리가 맞게 하고 폰 확인 목록에 넣는다. 색·글꼴·간격은 한 파일(테마)에 둔다. 메뉴를 웹으로 만들면 그 부분만 골격 4절 그대로.
- **입력**: **터치가 기본** — 가상 패드·버튼(엄지 닿는 곳·누르는 넓이 48dp 이상), Android 뒤로 버튼(일시정지·나가기 확인). 패드는 확장, 키보드는 개발 편의로만. 입력 표는 `docs/조작.md`.
- **수명주기**: 홈·전화·화면 꺼짐 → 일시정지·자동 저장·소리 멈춤 → 돌아오면 이어서. 저장은 앱 전용 저장소에 한다(외부 저장 권한을 쓰지 않는다). 권한은 최소로(인터넷은 온라인 기능이 있을 때만).
- **확인**(`howtoWORKFLOW.md` 2절 5단계의 게임판): 화면을 바꾼 Phase 는 정해 둔 장면을 같은 시드로 찍어 직접 본다 — 작업 서버에서는 창을 띄우지 않는 그리기(화면 없는 렌더링 — 예: 가짜 비디오 드라이버)로 찍어도 된다(화면 없는 전체 검증의 일부 · 게임 실행이 아니다). 화면·그림을 바꿨을 때만 찍고, 여러 장을 읽는 일은 10절대로 먼저 확인받는다. 기기 화면은 CI 에뮬레이터에서 찍고(CI 결과물), 사용자에게 폰 스크린샷 한 장을 부탁한다. 1280·390px 대신 기준 해상도와 가장 작은 기기. 남길 스크린샷은 테스트결과서 "화면 확인"에(4절 폰 확인).
- **성능 예산**(`docs/성능.md`): 목표 FPS(예: 60, 최저 30)·프레임 시간·메모리·첫 실행 시간·APK 크기·발열(10분 플레이) — 중급기(사용자 폰) 실측, 날짜·기기와 함께(`howtoWORKFLOW.md` 4절 "흔들리는 측정"). CI 에뮬레이터 수치는 참고만 한다(실기기와 다르다). 예산을 넘으면 그 Phase 는 완료 기준 미달이다.
- **접근성**: 색만으로 구분하지 않기·글자 크기·진동·번쩍임 끄기(있으면).

## 6. 자산 (`howtoDIRECTORY.md` 1·2절에 더함 — 일반 가이드에 없음)

- 그림·소리·글꼴·맵은 `assets/` 아래에 둔다. **원천(편집본)과 내보낸 것을 가른다** — 내보낸 것은 원천에서 다시 만들 수 있게 하고(`howtoDIRECTORY.md` 0절 "원천과 생성물을 가른다"), 내보내기는 스크립트로.
- **자산 출처 목록** `assets/ASSETS.md`(또는 `.json`): 파일·출처(직접 / AI 생성 — 도구·날짜 / 외부 — 이름·라이선스·주소 / 원작 참고 — 원작 위치)·쓰는 곳. 출처가 없는 자산은 검증이 잡는다. 원작이 있는 게임은 원작을 쓴 자산이 여기서 한 번에 모인다 — 배포 전에 사용자에게 보일 목록이다(7절).
- 다른 게임의 그림·캐릭터·음악·맵을 베끼지 않는다 — 장르 문법만 가져온다. 글꼴·효과음 라이선스가 앱 배포를 허용하는지 본다.
- **큰 파일**: GitHub 은 파일 하나 100MB·push 한 번 2GB 에서 막는다. LFS 를 쓸지는 착수 때 정한다(0절 — LFS 도 무료 분량이 있다). `git add -A`·`git add .` 대신 경로를 적고, 큰 묶음은 파일 수·크기를 먼저 보인다.

## 7. 빌드·배포·공개 (골격 7·11절·`howtoWORKFLOW.md` 1·6절에 더함)

- **빌드는 CI 에서**: 워크플로 파일 하나(`.github/workflows/<이름>.yml`)가 debug APK(수동 실행 — 빌드 검사용)와 서명한 APK(태그 — 릴리스에 붙인다)를 만든다. `versionCode` 는 늘 올리고 `versionName` 은 태그와 같게.
- **사용자가 받는 곳은 릴리스 하나**(골격 7절 "사용자가 받을 배포물"·`howtoWORKFLOW.md` 1절 "받는 사람이 고르는 곳에 둔다"): 태그를 올리면 CI 가 APK 를 GitHub Releases 에 붙이고, 사용자에게는 그곳만 안내한다(휴대폰 GitHub 앱의 릴리스에서 바로 받는다). 마일스톤 확인은 프리릴리스(예: `v0.3.0-rc.1`), 배포는 정식 태그. 휴대폰 GitHub 앱은 Releases 맨 위(Latest)를 먼저 보인다 — 폰 확인용 릴리스를 Latest 로 두어 바로 받게 해도 된다(태그 이름은 `-rc.N` 그대로). 어느 쪽인지 판마다 하나로 정해 골격 7절 "사용자가 받을 배포물"에 적는다. 릴리스 본문에는 폰에서 할 일(설치·1분 플레이 경로·확인 목록)을 적는다. 가지 빌드의 CI 결과물(Actions Artifacts)은 빌드 검사용이라 보존을 짧게(예: 1일) 두고 받으라고 하지 않는다. 태그를 올리는 것도 push 라 사람 확인이다(`howtoWORKFLOW.md` 6절).
- **릴리스에 붙이는 APK 는 늘 같은 서명 키로 서명한다.** 서명이 다르면 덮어 설치가 안 되고, 앱을 지우면 앱 전용 저장소의 세이브도 지워진다.
- **서명 키는 바꾸지 않는다.** 새로 만드는 배포(release) 키(keystore)는 커밋하지 않는다 — CI 비밀(Secrets)에 넣고 원본 보관 위치만 적는다(운영자가이드 8절 인수인계). 덮어 설치를 위해 고정 **디버그** 키를 비공개 저장소에 커밋해 온 판은 그대로 둘 수 있고, 릴리스에 붙이는 APK 도 그 키로 서명한다(같은 키를 Secrets 로 옮겨도 된다 — 키 자체는 그대로). 어느 쪽인지 CLAUDE.md 에 적는다. 잃으면 같은 앱으로 업데이트 설치가 안 되므로 백업을 둔다.
- **빌드 산출물(APK·AAB)은 커밋하지 않는다** — 릴리스에 붙인다. 지문(SHA-256)은 골격 7절·`howtoWORKFLOW.md` 1절 "받는 사람이 고르는 곳에 둔다" 그대로다(릴리스를 만드는 CI 가 빌드한 뒤 노트에 붙이고, 올라간 파일과 대조한다). 게임에서 더하는 것: 마일스톤 테스트결과서에 APK 파일 이름·크기·지문과 릴리스 주소를 적고, 옮겨 적은 지문은 릴리스 노트의 것과 대조한다(골격 4절 "옮겨 적은 것은 원본과 대조한다").
- **배포 기본 = 사용자 폰에 직접 설치(사이드로드).** 스토어(Google Play·App Store) 등록·남에게 주기·공개는 사람 확인이다(`howtoWORKFLOW.md` 6절 표에 더함). 스토어용 AAB 는 그때 만든다.
- 저장소는 비공개가 기본이다. 원작(IP)이 있는 팬게임은 원작 그림·대사를 넣은 빌드를 남에게 줄지 그때마다 사용자에게 묻는다(6절 출처 목록을 보인다).
- **배포 리허설**(`howtoWORKFLOW.md` 1절 "운영 빌드 리허설"의 게임판 — 사용자가 하고 결과를 알려 준다): 앱을 지운 폰에 릴리스의 APK 설치 → 첫 실행 → 1분 플레이 → 저장 → 종료 → 다시 불러오기 → 다음 릴리스로 업데이트 설치(옛 세이브 유지).

## 8. 공용 데이터를 받는 게임 (`howtoWORKFLOW.md` 4절 "여러 저장소가 모듈·데이터를 주고받을 때"의 게임판)

- 원본은 상류 한 곳이다. 받은 사본(도장 파일이 있는 폴더)은 손대지 않고, 받은 뒤 자기 시험(상류 골든 포함)을 통과시킨다.
- **id 로 참조**하고 이름 문자열을 코드에 박지 않는다. 세이브도 id 를 저장한다. 상류가 id 를 폐기하면(이어받는 id 표시) 세이브를 옮기는 코드와 시험을 둔다.
- 상류의 신뢰도 표기를 지킨다: 규칙·수치는 **확정 값만**, 추정 값은 이야기·연출에만. 원작에 없는 장면은 IF 로 표시한다.
- 고칠 것은 상류에 직접 쓰지 않는다 — 상류가 정한 '요청 목록' 양식(위치·파일:id·칸·지금 값·바랄 값·근거·급함)으로 사람에게 넘긴다.
- 상류 변경 기록의 '깨짐' 항목은 받을 때마다 읽고, 영향과 조치를 테스트결과서에 적는다.

## 9. 검증·마일스톤 보고 (`howtoWORKFLOW.md` 2절 9단계·`lessons-learned.md` 2절 교훈 1 에 더함)

- **전체 검증 하나 — 작업 서버에서 먼저, CI 가 다시**: 단위 + 통합(headless) + 상류 골든 + 받은 사본 해시 + 자산 출처 목록 + 문서 명령. 커밋 전 작업 서버에서 통과시키고(종료 코드 0), 병합은 CI 통과 뒤.
- APK 빌드·에뮬레이터 점검은 마일스톤 끝과 배포 전에 돌린다(수동 실행 또는 태그 — 분량·시간). 실패하면 그 Phase 는 끝나지 않은 것이다.
- **마일스톤 보고**(사용자에게): 되는 것·안 되는 것·시험 결과(작업 서버 검증 출력 원문·CI 실행 링크)·스크린샷(CI 에뮬레이터·사용자 폰)·릴리스 주소(APK)·1분 플레이 경로와 폰 확인 목록·성능 실측·다음 계획·예상 비용. 사용자 확인 뒤 다음 마일스톤으로 간다.

## 10. 토큰·비용 — 게임 고유만 (골격 11절 "토큰·비용"·`howtoWORKFLOW.md` 2·6절에 더함)

- 단계별 effort·비싼 단계 전 확인·사용량 측정(예상·누적·history)은 골격 11절 "토큰·비용"과 `howtoWORKFLOW.md` 2절 "단계마다 맞는 effort"·6절 표 그대로다. 게임에서 더하는 것만 적는다.
- **effort**: 일반 가이드 값(인터뷰·범위·구조 설계 최대, 문서·일반 구현 high, 반복 수정 medium)에 하나를 더한다 — 이미 있는 저장소의 첫 조사(2절 — 읽기 위주)는 medium.
- **그림 읽기가 가장 비싸다**(스크린샷·스프라이트·참고 그림·CI 스크린샷). 한 번에 묶어 읽고, 필요한 범위만, 축소로 충분하면 축소한다(글자·도트 판정처럼 정확해야 하면 1:1). 읽은 결과는 파일로 남겨 같은 그림을 다시 읽지 않는다. 그림을 여러 장 읽는 일은 `howtoWORKFLOW.md` 6절의 "토큰이 많이 드는 단계"로 보고 먼저 확인받는다.
- **CI 분량도 비용이다.** APK 빌드·에뮬레이터 점검을 여러 번 돌리는 일(여러 기기·API 수준 조합, 반복 실행)은 이유와 대략의 분량(분)을 먼저 말하고 확인받는다(1절).
