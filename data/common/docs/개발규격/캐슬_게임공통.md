## 1. 출력 · 토큰 · 크레딧 · 새 세션 · 자율 진행 (사용자 규칙 1~5 — castle_common CLAUDE.md 0절과 같다)

그 판 CLAUDE.md 에 같은 뜻의 규칙이 있으면 그것을 따르고, 없으면 이것을 그 CLAUDE.md 맨 앞(0절)에 넣는다(넣는 것은 첫 조사 때 사용자 확인 뒤).

1. **화면 출력**: 작업 중 메모 · 진행 한 줄은 영어로 짧게 써도 된다. 사용자가 읽을 글(설명 · 결과 · 답 · 선택 · 결정 · 확인 요청)은 한국어로, 작업이 끝난 뒤 **마지막에 한 덩어리**로 쓴다 — 구분선 한 줄 + 표지 하나(`## ✅ 결과` · `## 💬 답변` · `## ❓ 확인 요청`), 안은 `###` 소제목. 결정이 있어야 이어가면 ❓ 로 쓰고 거기서 멈춘다.
2. **토큰 효율**: 큰 작업(단계가 바뀔 때)을 시작하기 전에 한 번 제안한다 — ① 사전 읽기가 필요한가 ② 별도 프롬프트 파일이 필요한가 ③ 검토를 세분화할 가치가 있나(결정적 검사 · diff 로 대신할 수 있나) ④ 서브에이전트가 이득인가 ⑤ 단계별 effort. 지금 effort 가 과하면 그 자리에서 말한다(`claude --effort <low|medium|high|xhigh|max>`). 독립 작업은 묶고, 읽은 파일은 다시 읽지 않고, 큰 파일은 필요한 줄만 읽는다.
3. **크레딧**: 작업 전에 예상 $, 결과를 낼 때마다 예상 · 실제 · 누적 $(정가 기준 추정). 누적 기준일은 **2026-10-01 00:00**, 사용자가 refresh 를 말할 때까지 이어 쓴다. 한 번 작업(사용자가 승인한 한 묶음) 상한 **$1,000**(2026-11-06 답52) — 80% 에서 멈춰 보고하고, 100% 면 즉시 중단한다. 예상이 $40 을 넘으면 $40 안쪽 배치로 쪼갠 계획을 먼저 보인다. 다음 세션이 이어 보게 기록을 남긴다. 측정 도구는 그 판 CLAUDE.md 가 정한다 — castle_common `tools/credit.py` 는 castle_common 폴더에서 연 대화만 센다(그 판에 도구가 없으면 첫 조사 때 사용자에게 묻는다).
4. **새 세션을 권할 때**: 단위 작업이 끝나 지금 `/exit` · `/clear` 해도 되는지(남은 일 · 커밋 여부)와 새 세션에 붙일 **첫 프롬프트 전문**(코드 블록)을 적는다 — 짧은 답이라도 매번.
5. **추천대로 자율 진행**(2026-11-06 답53): 갈리는 곳은 추천값으로 진행하고 기록만 남긴다 — 사용자에게 묻고 멈추는 것은 effort 상향이 필요할 때만. 단위 작업이 끝나면 커밋 · push 한다. 히스토리 재작성 · force push · 원격 삭제 · 공개 전환은 그 자리 지시 없이 하지 않는다.

## 2. castle_common 과의 약속 (옛 기획서 00 11절 1~8 + 넓힘)

1. **첫 작업은 조사**다. 자기 저장소의 `CLAUDE.md` · 문서 · 코드 · 테스트 · 빌드 설정 · CI 를 읽고 `docs/기획_차이.md`(기획서와 다른 점 · 이미 있는 것 · 없는 것 · **규격과 다른 점**)를 만든 뒤 멈추고 사용자에게 보인다. 조사 전엔 코드를 고치지 않는다.
2. 자기 저장소 `CLAUDE.md` 의 규칙(출력 · 비용 · 커밋 · 테스트)을 따른다 — 이 규격과 다르면 1항의 '규격과 다른 점'으로 묻는다.
3. **castle_common 은 읽기만** 한다. 고칠 것(데이터 오류 · 필요한 칸 · 새 사건 · 규격)은 3절 양식으로 사용자에게 넘긴다 — castle_common 세션이 고친다. 받은 사본(`SOURCE.json` 이 있는 폴더)은 손으로 고치지 않는다.
4. **받기**: castle_common 에서 `python3 -B tools/sync.py <판 id>`(Windows 는 `py -3.12`) — check 통과 · 커밋 뒤에만 된다. 받는 파일 · 받는 곳은 `games.json` 이 정한다(castle_M = `data/` · `cases/` · `canon/` · 이 묶음(2026-11-06), castle_M3D = `data/` · `cases/` · `canon/` · 이 묶음, castle_srpg = `data/` · `cases/` · `canon/` · 대사 원문 화 파일(`work/text/`) · 이 묶음, castle_strategy = `data/` · `cases/` · `canon/*.json` · `packs/strategy/` · 이 묶음(2026-11-10), castle 취호전 = `canon/` · `data/looks.json` · 이 묶음 — castle_tactics 는 no-sync). 받은 뒤 자기 시험(2층 규칙을 따르는 판은 `cases/` 포함)을 통과시키고, castle_common README '반영 현황' 갱신 거리는 목록으로 넘긴다(castle_common 세션 몫).
5. **id 로 참조**하고 이름 문자열을 박지 않는다. 세이브는 id 를 저장한다. `deprecated: true` 면 `replaced_by` 를 따라간다(같은 파일이면 id · 다른 canon 파일이면 `파일:id` · `null` 이면 이어받는 것 없음) — 세이브 옮기기 시험을 둔다.
6. **신뢰도**: 1 · 2층 값(등급 · 승급 · 비용 · 규칙)은 사용자 확정만 쓴다. canon 의 `conf: ai` · `guess` 는 이야기 · 연출에만(표시와 함께). 원작에 없는 장면은 IF 로 표시한다(결정 8).
7. **CHANGELOG** 의 [값] · [추가] · [깨짐] · [canon] 을 받을 때마다 읽는다. [깨짐] 은 영향 · 조치를 테스트결과서에 적는다.
8. **원작 내용을 물을 때** 위치는 `화/컷`(`078/041` · `078/041@340` · `077/017-031` — 화 = 원본 폴더 번호 3자리, 컷 = 자른 조각 번호, 1부는 `p1:061/021`)으로 적고 **화 → 컷 오름차순**으로 번호를 매긴다(여러 곳을 가리키면 가장 앞). 묶음 번호(`c1` 등)는 위치로 쓰지 않는다. 화 번호는 폴더 번호다 — 디시 · 팬 글의 공식 회차 + 1 = 폴더(1 · 2부 모두 프롤로그가 001). 판 문서(예: 공유 `docs/story/`)가 공식 회차를 쓰면 그 문서 머리에 적고, castle_common 에 물을 때 폴더 번호로 바꾼다(castle_M 요청 12).
9. **원작 컷 · 대사**: 대사는 원문 그대로 써도 된다(사용자 답32). 원작 컷도 필요하면 쓸 수 있으나, 받기는 `games.json` `receives` 로 정한다(사용자 확인). **배포 빌드에는 넣지 않는 것이 기본** — 개인 빌드만, 남에게 줄 때 다시 묻는다(결정 5). 원작 컷을 쓴 자산은 `assets/ASSETS.md` 에 원작 위치(`화/컷`)로 적는다.
10. **비공개 · 개인용** — 판 저장소는 모두 private, 공개 전환 금지. 원작 내용(대사 · 컷 · canon · 이 문서)은 이 저장소들 밖으로 올리지 않는다.
11. 다른 게임의 그림 · 캐릭터 · 음악 · 맵을 베끼지 않는다 — 장르 문법만 가져온다.
12. **마일스톤 보고** — 되는 것 · 안 되는 것 · 시험 결과(작업 서버 검증 출력 · Actions 기록) · APK(릴리스 주소) · 폰 확인 · 다음 계획 · 예상 비용(`게임개발규격.md` 9절) → 사용자 확인 뒤 다음으로 간다.
13. 경로 · 실행기를 하드코딩하지 않는다 — 판들은 Windows(`D:\claude\fun\…`)와 Linux 에서 열린다. castle_common 은 판 저장소 옆 폴더(`../castle_common`)다.
14. 커밋 · push · 히스토리 재작성 · 원격 · 공개 범위는 그 판 CLAUDE.md 규칙을 따른다 — 정한 게 없으면 사용자가 시킬 때만. 여러 서버 · PC 에서 같이 작업하므로 commit · push 전에 `git fetch` 로 원격 새 커밋을 먼저 받는다(사용자 2026-11-04 답41).
15. **플랫폼 · 실행 · 시험 — 기획서 00 결정 10(답39)**: **모바일(Android) 전용** — PC판(PyInstaller · Windows 내보내기) · PC 조작 전용 기능 · iOS 는 만들지 않는다(키보드는 개발 중 편의로만). 실행 · 시험은 GitHub 에 올려 Actions(`.github/workflows/android.yml` — APK 빌드 · 자동 시험 · 에뮬레이터 점검)로 하고, **사용자가 폰에 설치할 APK 는 릴리스(태그) 하나로만 안내한다** — 태그를 올리면 Actions 가 APK 를 GitHub Releases 에 붙이고, 사용자는 휴대폰 GitHub 앱의 릴리스에서 받는다(마일스톤 확인은 프리릴리스, 예 `v0.3.0-rc.1` · 늘 같은 서명 키). 가지 빌드의 Actions 아티팩트는 빌드 검사용이라 보존 1일(`retention-days: 1`)로 두고 받으라고 안내하지 않는다. 태그 push 도 사람 확인이다(결정 10 덧붙임 3 · `게임개발규격.md` 7절 — agentic-sdlc 골격 7절 '사용자가 받을 배포물'). 작업 서버에서는 게임 실행 · Android 빌드 · 에뮬레이터를 돌리지 않는다 — **화면 없는 자동 검증(전체 검증 명령 — 단위 + headless 통합)은 작업 서버에서도 돌린다**(답42 · 각 판 `.venv` · `.tools` 를 둔다). 시험 결과는 작업 서버 검증 출력 · Actions 기록(로그 · 스크린샷 — 남길 것은 저장소로 옮긴다)과 사용자 폰 확인으로 보고한다. Actions 무료 분량(비공개 저장소 · 계정 전체 월 2,000분)을 판들이 같이 쓰므로 push 마다 빌드하지 말고 경로 필터 · 수동 실행(`workflow_dispatch`)으로 아낀다. `games.json` 각 판 `platforms: ["android"]`(check 가 다른 값을 막는다). iOS · desktop 확장은 사용자가 새로 정할 때만(답40 "필요시 ios와 desktop으로 확장" — 지금은 정하지 않았다).

## 3. 고칠 거리 양식 — 판 → castle_common

- 파일: 각 판 `docs/castle_common_요청.md`(누적). castle_common 이 반영하면 그 줄을 지운다.
- 넘기는 법: 사용자가 그 파일 내용을 castle_common 세션에 붙여 넣는다(같은 PC 면 경로만 알려 줘도 된다). castle_common 세션은 화/컷 순으로 정리해 ❓ 로 묻고 반영한다.
- 순서: 원작 위치가 있는 줄은 **화 → 컷 오름차순**, 없는 줄(데이터 칸 · 규격)은 그 뒤에 `파일:id` 순.
- 2층 수치 · 등급 배치 · 새 인물 등급은 '바랄 값'에 후보만 적는다 — 확정은 사용자다(castle_common CLAUDE.md 9절).
- 급함: **막힘**(그 판 진행이 멈춤) · **다음 마일스톤** · **언젠가**.
